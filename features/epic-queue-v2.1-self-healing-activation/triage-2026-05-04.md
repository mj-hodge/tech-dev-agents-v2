## Section 5 — Gaps observed (file as `EPIC-Queue-v2.1-FU-*` follow-ups)

1. **No `/api/dispatch/v2/events/{job_id}` endpoint to fetch the failed-event payload.**
   `/api/dispatch/v2/lineage/{job_id}` returns only `{job_id, attempt, state, parent_job_id, redispatched_at}` — no `event_data`, no `failure_reason`, no `error_message`. Triage right now has to either log into PG or guess from the queue-row metadata. **Proposal:** add `GET /api/dispatch/v2/events/{job_id}` returning `[{event_id, event_type, event_data, actor, created_at}, ...]` (read-only, MANAGER role).

2. **STORY-857 SIGTERM-handler patch on `dispatch_poller_v2.py` is in the working tree but not deployed.**
   `git diff HEAD -- deployment/hermes/dispatch_poller_v2.py` shows the `_handle_sigterm`, `_active_lease_path`, drain-leases support is uncommitted/undeployed. The `.deploy-manifest.json` hash for `dispatch_poller_v2.py` doesn't even include the file. Until that ships and is deployed, every `push-code.sh` restart will continue to orphan in-flight leases — meaning every cluster-2-style cascade is reproducible at every deploy. **Proposal:** commit + deploy STORY-857 before any further `push-code.sh` runs against the fleet.

3. **`dispatch_expired_lease_sweeper` only deletes rows from `dispatch_leases`** — it cannot recover jobs whose state machine says `leased` but whose `dispatch_leases` row was never written or was deleted by a parallel path. STORY-828/829 are in this state. **Proposal:** sweeper should also detect `state=leased AND lane=in_progress` rows in `dispatch_state_current` whose `updated_at` is > 30 min old AND there is no row in `dispatch_leases`, and emit a `released` event for those.

4. **`STORY-V2-SMOKE` smoke-test row has no auto-cleanup.** A test row enqueued 01:47 May 3 sat for 22 hours and then got swept up in cluster 2. Either smoke-test rows should be tagged (e.g. `enqueued_by='mark-test'` already gives us the signal) and auto-completed/auto-cancelled by the smoke-test harness, or the sweeper should age them out.

5. **Failure-cluster correlation needs first-class observability.** This entire triage was reconstructed from `/queue` + `journalctl` + git history. The data points (failures per minute, restart events per agent, lease-orphan count) are all in PG / systemd already; an AlertStatusPanel or `/api/dispatch/v2/health` endpoint that surfaces "N failures in last 10 min, M recent restarts" would have flagged cluster 1 in real time.

6. **No structured failure_reason in `attention_queue` API response.** The `/queue` payload includes `failure_class` ("phase_runner_crash") but not the `failure_reason` text. For triage, knowing whether the crash was an `argparse_reject`-pattern miss vs a real Python exception is the difference between "requeue" and "investigate". **Proposal:** include `failure_reason` (truncated) and `last_event_id` in the `/queue` row, OR pair this with gap #1 (`/events/{job_id}`).
